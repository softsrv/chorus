# Architecture

Chorus is structured into three main parts, plus an out-of-process system testing suite (`systest`) and architectural decision records (ADRs).

## The Three Parts

### 1. `cmd/app`
`cmd/app` serves as the bootstrap entrypoint only (`cmd/app/main.go`). It handles:
- Configuration loading and environment validation
- Database connection pool setup (`pgxpool`)
- Dependency wiring and service instantiation
- Background workers:
  - `RunTokenCleanup`: Periodic expired token cleanup
  - `RunQuestExpiry`: Periodic quest expiry sweeps
  - `RunQuestRollover`: Midnight end-of-day expiry and quest rollover/assignment
- HTTP server configuration and graceful shutdown on `SIGINT` / `SIGTERM` signals

`cmd/app` sits at the top of the dependency graph and is imported by nothing.

### 2. `internal/*`
The core application packages implement business logic, HTTP routing, and data access:
- **HTTP Layer:**
  - `internal/http/router.go`: Route registration, middleware chain, and rate limits
  - `internal/http/handlers/`: JSON request/response handling, DTO mappings (`dto.go`), and error-to-status mapping (`json.go`)
  - `internal/http/middleware/`: Bearer token authentication, panic recovery, rate limiting, security headers, request body limits, logging, and request IDs
  - `internal/http/respond/`: Standard JSON response and error envelope helpers shared by handlers and middleware
- **Application Services:**
  - `internal/app/`: Domain services containing business rules, authorization checks, and validation
- **Data Access:**
  - `internal/db/`: Code generated by sqlc from queries in `db/queries/`; never edited by hand
- **Leaf Packages:**
  - `internal/auth`: Token minting and password hashing utilities (imports no chorus package)
  - `internal/users`: User model helpers (imports no chorus package)
  - `internal/email`: Email delivery and mailer abstractions (imports no chorus package)
- **Test-Only Packages:**
  - `internal/testnet`: Test-only helper to refuse outbound dials (`RefuseExternal`)
  - `internal/archtest`: Architectural boundary tests enforcing allowed import rules

### 3. `web`
The web client (`web/static/`) is an embedded vanilla-JS web test client (HTML and vanilla JS modules, with no frontend frameworks).
- In development, assets are served from disk.
- In production, assets are embedded directly into the Go application binary.

## System Testing (`systest`)

`systest` is an out-of-process black-box testing suite. It runs in its own test package and imports no chorus production or internal packages. Instead, it executes the compiled `cmd/app` application binary (or the built Docker image) over loopback HTTP, sending real SMTP emails to an in-test capture server and interacting with real Postgres instances.

## Dependency Direction

Chorus enforces strict architectural boundaries across its packages.

In prose, the dependency direction flows downward:
- `cmd/app` sits at the top, orchestrating dependencies, and is imported by nothing.
- The HTTP layer (`internal/http`, `internal/http/handlers`, `internal/http/middleware`) depends on application services (`internal/app`), data models (`internal/db`), and response helpers (`internal/http/respond`).
- Application services (`internal/app`) depend on data models (`internal/db`) and leaf utility packages (`internal/auth`, `internal/users`, `internal/email`).
- Leaf packages (`internal/auth`, `internal/users`, `internal/email`, `internal/db`, `internal/http/respond`) import no chorus package.
- Web client scripts (`web/static/js/`) resolve internally or use `node:`-prefixed builtins; web JS never reaches `internal/` or `cmd/`.

The single enforced source of truth for these import rules is defined in `internal/archtest/boundaries_test.go` via `prodAllow` (for non-test production code) and `testExtra` (for test-specific allowances). These boundaries are continuously enforced by running:

```bash
make boundaries
```
